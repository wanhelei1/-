# 政企顾问需求访谈

## 用途

形成可进入POC与方案评审的需求矩阵，明确未知项和责任人。

本文件用于训练与生成，不直接替代具体型号事实。任何参数、功能、支持范围、服务和动态信息都要回到相应来源；资料不足时允许给出有限结论和验证计划，不为追求顺畅话术补造信息。

## 使用情境

客户提出‘安全、稳定、易维护’，但会议上只有采购与业务代表，IT和安全人员尚未加入。

## 开始前准备

- 记录用户原话、任务频率、不能接受的风险和期望完成时间。
- 获取完整型号/SKU、系统与软件版本；涉及外设时记录品牌、型号、接口和连接链路。
- 打开P1事实、P7支持与必要的厂商官方页面，不用记忆或搜索摘要代替原页。
- 将价格、库存、赠品、服务权益和交期放进单独的动态字段，并标注核验人和时间。

## 关键问题树

### 1. ‘安全’对应哪些制度、产品或认证要求？

**为什么要问：** 把抽象词转成可验证条款。如果这一项无法确认，不应把受它影响的参数、兼容性或推荐写成确定结论。

### 2. 业务中断的影响和恢复时间是什么？

**为什么要问：** 决定备机与服务流程。如果这一项无法确认，不应把受它影响的参数、兼容性或推荐写成确定结论。

### 3. 哪些应用和外设不可替换？

**为什么要问：** 形成硬门槛。如果这一项无法确认，不应把受它影响的参数、兼容性或推荐写成确定结论。

### 4. 谁有权修改网络、证书和镜像？

**为什么要问：** 确定试点权限。如果这一项无法确认，不应把受它影响的参数、兼容性或推荐写成确定结论。

### 5. 现有数据和账号怎样迁移/回收？

**为什么要问：** 控制上线与退出。如果这一项无法确认，不应把受它影响的参数、兼容性或推荐写成确定结论。

### 6. 采购、验收和运维分别由谁签字？

**为什么要问：** 建立决策链。如果这一项无法确认，不应把受它影响的参数、兼容性或推荐写成确定结论。

## 执行步骤

1. 把业务、技术、安全、采购四类访谈分开记录。完成后把结果标成‘已确认 / 待测试 / 不适用’，并附证据位置。
2. 对缺席角色的问题指定负责人和日期。完成后把结果标成‘已确认 / 待测试 / 不适用’，并附证据位置。
3. 需求写成可测试句子，不保留‘好用’‘稳定’等空泛词。完成后把结果标成‘已确认 / 待测试 / 不适用’，并附证据位置。
4. 每个门槛对应测试输入和通过标准。完成后把结果标成‘已确认 / 待测试 / 不适用’，并附证据位置。
5. 访谈结束输出冲突项与下一次会议议程。完成后把结果标成‘已确认 / 待测试 / 不适用’，并附证据位置。

## 完整示范

**情境：** 客户提出‘安全、稳定、易维护’，但会议上只有采购与业务代表，IT和安全人员尚未加入。

**示范处理：** 顾问不回答‘绝对安全’，而是追问具体基线、证书、网络和审计要求；对暂未到场的安全部门，列出待确认问题并暂停相关承诺。POC只验证已批准的场景，结论标注环境与版本。

**建议收口：** ‘以上结论只对应已经确认的型号、版本和任务；未确认项已列入验证清单。你可以带常用文件、软件版本或外设完成实机核验，价格与权益则以当日授权页面或结算信息为准。’

## 正确表达与错误表达

- 正确：先给有限结论，再说明证据、适用条件和下一步。
- 正确：主动说出不适合的人群或需要先验证的门槛。
- 错误：‘肯定都能用’‘全系都是这个配置’‘任何情况都可以’。
- 错误：虚构第一人称体验、用户评价、销量、库存或无法核验的效率百分比。

### 本主题常见错误

- 把采购代表的口头偏好当成技术标准
- 客户说‘国产化’就自行推断操作系统和应用要求
- 未确定数据边界就安排样机导入真实资料
- 没有给未知项指定确认人和截止时间

## 证据路径

- 客户需求与制度文件
- P8企业IT及行业案例
- P1/P7官方证据
- P4获授权报价与合同字段模板

## 输出记录模板

- 用户/客户任务：
- 完整产品与SKU：
- 系统、软件、插件和外设：
- 必须满足 / 希望改善 / 可以放弃：
- 已确认事实、来源与日期：
- 待核验项、影响与责任人：
- 候选方案及各自取舍：
- 演示或试点步骤与通过标准：
- 动态价格/库存/权益核验人和时间：
- 最终答复与下一步：

## 发布或交付前检查

- □ 型号、SKU、系统路线和版本没有混用。
- □ 每个数字都能回到当前适用的官方页面，并保留限定词。
- □ 第三方案例只用于研究问题与结构，没有当成产品事实。
- □ 体验来自真实、获授权的测试，没有伪造人物或使用时长。
- □ 价格、库存、活动、交期和服务权益带有日期与责任人。
- □ 已说明限制、不适用情形、待核验项和转人工路径。
