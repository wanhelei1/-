# 选型与版本 FAQ｜先锁任务，再比较具体销售配置

> 本指南不是型号排行榜。它用于把系统、任务、形态和配置约束整理成候选与验证计划。  
> 证据基准日：2026-10-17；在售状态与销售配置以查询当天官方页面和渠道为准。

## 适用范围

适用于个人、家庭、小团队和企业采购前的型号初筛，尤其是同名不同年份、鸿蒙与 Windows 路线、不同屏幕/内存/存储版本以及轻薄、大屏、折叠或高性能形态的选择。它不根据型号名称、处理器等级或宣传词直接给赢家，也不在缺少软件与外设需求时替用户决定系统。

选型要区分“必须满足”“希望满足”“可接受代价”。关键软件、文件格式、企业管理与安全通常是必须项；重量、屏幕、接口和续航可能需要排序；预算、活动和库存是动态采购变量。若必须项未验证，后面的参数比较没有决策意义。

## 判断树

```text
开始选型
├─ 是否有必须软件、企业策略或专用外设？
│  ├─ 有 → 先锁系统/架构/驱动支持；不满足者退出候选
│  └─ 无 → 比较日常任务与协同生态
├─ 主要空间与移动方式？
│  ├─ 高频通勤 → 实测整套携带重量、充电与接口
│  ├─ 固定工位 → 关注屏幕、键盘、外接显示与传统接口
│  └─ 多形态/多窗口 → 验证姿态、输入、窗口与软件适配
├─ 工作负载能否具体化？
│  ├─ 否 → 先用文件规模、并发应用、输出目标重写任务
│  └─ 是 → 按任务锁内存、存储、图形与散热验证
├─ 候选是否锁到销售配置？
│  ├─ 否 → 不比较价格和体验，先取 SKU
│  └─ 是 → 建立逐项事实表与 POC
└─ 核心任务是否通过？
   ├─ 否 → 淘汰或记录经批准的替代路径
   └─ 是 → 再比较便携、显示、接口、服务与总成本
```

## 步骤与追问

### 1. 系统与生态先行

列出必须应用的完整名称、版本、插件、许可证、文件格式和专用硬件；企业用户再列域/账号、证书、VPN、终端管理、加密、打印和日志。分别查厂商对目标系统与架构的正式支持。鸿蒙与 Windows 可以在相同业务任务下比较，但不能共享菜单、驱动、应用和协同结论。

### 2. 用一天的任务描述性能需求

记录同时运行的应用、典型文件大小、表格行数、网页数量、代码或模型规模、视频分辨率/编码、是否持续满载、预计本地数据量和输出时限。处理器名称只作为配置事实；是否合适要通过目标项目完成率、稳定性、内存/存储余量和输出核验判断。没有同口径实测时不写“快多少”。

### 3. 把显示与形态变成场景

追问每天携带距离、是否站立/腿上使用、桌面深度、窗口数量、触控/手写、阅读或色彩任务、外接显示器数量与目标信号。尺寸、分辨率、比例、亮度、色域、刷新率、触控和表面处理是不同维度；折叠或双屏形态还要验证姿态切换、键盘、支撑和应用窗口重排。

### 4. 逐端口核对真实外设

列出显示器、扩展坞、移动盘、鼠标、耳机、网线、打印机、采集卡和充电器，画连接拓扑。核对电脑端口的协议而非只看外形；目标分辨率/刷新率、供电、数据速率和多设备并用均需验证。包装中的转接线或附件也要按具体版本确认，不能把典藏版或可选附件套到标准版。

### 5. 锁定销售配置并做差异表

对每个候选记录完整产品名、年份/代次、系统、处理器、内存、存储、屏幕版本、电池、官方重量口径、接口、键盘与随附附件。事实必须来自该型号产品/规格页或 P1 对应卡片。遇到“最高、可选、约、起始、仅某系统”保留原词；页面没有的字段写空缺，不从相邻型号补。

### 6. 做任务 POC 与权重决策

至少准备一个核心任务、一个移动/会议任务和一个外设/协同任务。使用同一素材、账号、网络和外设；记录成功、条件成功或失败。只有必须项通过后，才按用户自己确认的权重比较便携、显示、接口、续航、服务和采购成本。权重变化会改变结果，因此答案应说明适合哪类任务，而不是给普遍排名。

选型表还应保留“退出理由”：候选可能因系统不支持、端口协议不足、目标软件无官方结论、携带组成超限或企业策略不允许而退出。退出理由只针对当前任务，不等于产品整体不好；需求变化后可以重新评估。这样既能防止把一次结果写成永久排名，也能解释为何某个参数更高的型号没有进入最终候选。

## 验证与完成标准

候选清单完成的标准是：每台都锁到可购买或可借测的具体 SKU；十项核心字段有来源或明确缺口；必须软件与外设有厂商证据；系统与企业条件通过负责人确认；核心 POC 有输出文件、日志和失败记录；动态价格与库存有查询时间。最终建议应能解释“为何入选、适用哪些任务、不能承诺什么、购买前还要确认什么”。

续航只在锁定配置、亮度、网络、负载和电源策略下记录本次测试，不将官网实验室时长直接换算。重量要区分主机、适配器、键盘/支架和常用转接。存储要预留系统、缓存与项目增长；是否可升级只有官方明确或授权服务确认后才写。

## 失败分支

- 同名型号参数冲突：检查年份、系统、地区和 SKU；分别保留来源，不拼成一台“全能配置”。
- 必须软件没有目标系统支持：该候选退出原生工作流，除非业务和安全批准远程/网页替代。
- 预算先锁但任务不清：先给需求表和不同取舍，不为凑预算假定能力。
- 官网只给系列最高配置：不能视为本次 SKU；向渠道索取完整配置。
- 用户被单一参数吸引：回到任务验证，解释该参数不覆盖软件、接口、散热与续航。
- 候选无法借测：把未验证风险显式列入，不以评测或口碑替代关键 POC。

## 风险升级

批量采购、关键业务替换、跨系统迁移、专业生产软件、企业证书/加密、特殊无障碍需要、长期备件或 SLA 要求，应升级给 IT、采购、业务、软件厂商和华为官方联合评审。配置/政策页面冲突或渠道无法提供 SKU 时，不签署确定性技术承诺。涉及刷机、拆机升级、非官方镜像或绕过安全策略的建议立即停止。

## 记录字段

用户角色与任务、必须/希望/可接受条件、软件和版本、文件规模、外设拓扑、企业策略、候选完整型号/SKU、系统、处理器、内存、存储、屏幕、电池、重量口径、接口、附件、来源与日期、字段缺口、POC 环境/结果、动态价格时间、风险责任方、最终适用场景和复核人。不要在对外表格保存完整 S/N、账号、许可证或企业证书。

## 候选矩阵与决策会议模板

### 先设淘汰门槛

选型会议先确认不可妥协条件，例如必须运行某版本软件、必须连接两台指定显示器、必须通过企业证书/VPN、必须离线完成核心任务或整套携带重量上限。每个条件都写验证证据和负责人。任一门槛失败，候选先退出当前场景，不进入“用更高内存弥补系统不支持”一类无效讨论。

门槛通过后再列偏好：屏幕面积、触控、键盘、接口数量、噪声、适配器、协同、服务和预算。偏好可设高/中/低优先级，但不要用无来源的综合分把差异隐藏。若团队成员权重不同，保留各角色视角，例如移动人员看携带，创作者看项目与显示，IT 看管理和恢复，采购看 SKU、交期和服务；最终决策记录谁接受了什么取舍。

### 建立逐项事实矩阵

行使用系统、处理器、内存、存储、屏幕、重量、电池、接口、协同、附件、服务和动态采购信息；列是具体 SKU。每个单元格由“事实—来源—日期—限定—待验证”组成，不能只填一个数字。若一侧缺字段，写空缺并形成补证任务；不要为了表格整齐从其他年份或高配型号借数值。

系统和软件矩阵单独列：应用版本、原生/网页/远程路径、插件、授权、文件格式、驱动、企业策略和 POC。端口矩阵单独列实际外设拓扑。续航矩阵只记录目标负载下的本轮结果和条件，不把不同官网测试相减。这样可避免一张总表把口径不同的内容伪装成精确比较。

### 三轮筛选

第一轮做纸面证据筛选，排除明确不支持或身份不清；第二轮用样机完成核心软件、外设和协同 POC；第三轮在真实一天或代表性时段验证携带、会议、充电、工位切换和数据交付。每轮结束都有“进入/条件进入/退出/待补证”，并记录原因。价格和活动放在技术可行候选形成之后核对，避免因为短期优惠保留不满足必须任务的设备。

### 决策输出

最终文件不是“第一名”，而应是“对任务 A，候选 X 在这些条件下通过；对任务 B，候选 Y 仍有这些风险”。同时给购买时的复核清单：完整 SKU、系统、屏幕版本、附件、渠道、动态金额和退换条件。若只允许选一台，写明被接受的缺口和补救措施，如备用设备、远程工作站、转接器或培训，并指定成本与责任方。

三个月或重大版本更新后复核关键软件与服务；批量采购可先小规模试点，观察更新、驱动、镜像、账号、外设和支持流程。试点成功只覆盖相同 SKU 和环境，渠道更换配置后应重新核验，不能把旧样机结论自动复制。

决策会议结束时安排一名未参与测试的人按记录重新找到来源和 POC 输出。如果他只能看到结论、找不到完整配置或失败条件，就不应批准采购。候选被替换、配置缺货或软件升级时，重新走受影响的门槛和任务，不必重做无关项目，但要明确继承了哪些证据。
